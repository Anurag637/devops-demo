1 Introduction

In contemporary DevOps practices, software reliability relies heavily on packaging consistency and automated lifecycle management. Containerization is an OS-level virtualization method used to deploy and run distributed applications without launching an entire virtual machine (VM) for each application. Multiple isolated user-space instances (containers) share the host OS kernel, offering minimal memory overhead and near-instantaneous startup times.

Docker provides the industry-standard developer tooling to package code, runtimes, system tools, and libraries into portable Docker Images.

However, in real-world distributed architectures, running standalone containers manually introduces vulnerabilities related to high availability, autoscaling, network routing, and automated self-healing. This is where Kubernetes (K8s) operates: it abstracts underlying hardware into an orchestration cluster, managing container scheduling, replicas, rollouts, service discovery, and health checks across computing nodes.

6 Dockerfile Specification

The container specification file Dockerfile packages the application into an immutable container image:

FROM nginx:latest COPY index.html /usr/share/nginx/html/index.html EXPOSE 80 CMD ["nginx", "-g", "daemon off;"]

Directive Explanation Table

Instruction Argument Technical Purpose
FROM nginx:latest Initializes the build stage using the official Nginx Alpine/Debian base image containing the web server binary.
COPY index.html /usr/share/nginx/html/ Transfers the custom index.html from the local build context into Nginx's default public document root.
EXPOSE 80 Documents that the container process listens on TCP port 80 at runtime.
CMD ["nginx", "-g", "daemon off;"] Instructs Nginx to run in the foreground. This prevents PID 1 from exiting, ensuring the container remains active.
Efficiency Note: Using nginx:latest as a parent image ensures a lightweight footprint (~187MB uncompressed), ultra-fast deployment time, and hardened security defaults.

11 Kubernetes Deployment Manifest

The declarative configuration for orchestrating pod instances is specified in deployment.yaml:

apiVersion: apps/v1 kind: Deployment metadata: name: docker-lab-deployment labels: app: docker-lab spec: replicas: 2 selector: matchLabels: app: docker-lab template: metadata: labels: app: docker-lab spec: containers: - name: docker-lab-container image: docker-lab-app imagePullPolicy: Never ports: - containerPort: 80

Specification Parameter Breakdown

YAML Field Configured Value Architectural Role
kind Deployment Declares that this manifest configures a high-level Deployment controller managing a ReplicaSet.
spec.replicas 2 Instructs the controller to maintain exactly 2 concurrent healthy pod instances.
selector.matchLabels app: docker-lab Defines the selector query used by the controller to discover and group pods.
imagePullPolicy Never Enforces using the local Docker daemon image cache without attempting external Docker Hub lookups.
containerPort 80 Designates the TCP port on which the containerized application is listening.

12 Kubernetes Service Manifest

The networking proxy configuration is defined in service.yaml:

apiVersion: v1 kind: Service metadata: name: docker-lab-service spec: type: NodePort selector: app: docker-lab ports: - protocol: TCP port: 80 targetPort: 80 nodePort: 30080

NodePort Role: Allocates a static port (30080) on the Minikube cluster node, enabling external web traffic to reach the pods.

20 Conclusion

In this laboratory experiment, a complete end-to-end containerization and Kubernetes orchestration workflow was demonstrated:

  1. Containerization: Docker successfully containerized the web application into a portable, immutable image (docker-lab-app), ensuring identical execution across distinct operating environments.
